# Chapter 2. Monorepo 안에서 패키지 독립성과 공통화를 설계하기

namuwiki_trend를 만든 뒤 google_finance를 추가하려고 하자, 먼저 저장소를 어떻게 구성할지 결정해야 했습니다. 여러 패키지를 하나의 Git 저장소에서 관리하는 Monorepo로 둘 수도 있었고, 새 자동화마다 저장소를 따로 만들 수도 있었으며, 하나의 Python 패키지 안에 모든 기능을 넣을 수도 있었습니다. 두 자동화는 Python과 일부 개발 도구를 공유했지만, 수집 대상과 데이터의 의미는 달랐습니다.

이 문제는 디렉터리 이름을 정하는 일이 아니었습니다. 한 저장소에서 함께 관리하면 개발 환경과 검증 방법을 공유할 수 있지만, 잘못 나누면 서로 다른 도메인의 코드와 설정이 섞일 수 있습니다. 반대로 저장소를 완전히 분리하면 경계는 선명해지지만, 개인 프로젝트에서 같은 환경과 문서를 여러 번 관리해야 합니다.

이 Chapter의 질문은 하나입니다.

> 서로 다른 자동화 패키지를 하나의 Monorepo에서 관리할 때, 무엇을 공통으로 관리하고 무엇을 각 패키지의 책임으로 남겨야 하는가?

## 두 번째 자동화를 추가하면서 생긴 문제

namuwiki_trend는 나무위키의 실시간 검색어를 수집하고 뉴스와 LLM 문맥을 결합합니다. google_finance는 Google Finance에서 한 종목의 시세를 수집하고 저장합니다. 같은 자동화라는 공통점은 있지만, 외부 시스템과 데이터의 의미는 다릅니다.

처음부터 하나의 구조로 묶으려 하면 다음과 같은 문제가 생길 수 있습니다.

- 한 패키지의 모델 변경이 다른 패키지에 영향을 줄 수 있습니다.
- 서로 다른 외부 시스템의 오류 정책이 하나의 공통 흐름에 섞일 수 있습니다.
- 패키지 하나를 실행하기 위해 다른 패키지의 내부 구현을 알아야 할 수 있습니다.
- 공통으로 보이는 파일 구조가 실제 책임의 차이를 가릴 수 있습니다.

반대로 저장소를 매번 새로 만들면 다른 비용이 생깁니다.

- Python 버전과 개발 의존성을 반복해서 관리해야 합니다.
- 테스트와 lint 실행 방법이 저장소마다 달라질 수 있습니다.
- 이전 자동화에서 얻은 설계 원칙과 검증 절차를 다시 정리해야 합니다.

따라서 두 번째 패키지를 추가하는 시점에는 “같이 둘 것인가”보다 “어떤 경계를 유지하면서 같이 둘 것인가”가 더 중요한 질문이 됩니다.

## 저장소를 구성할 수 있었던 세 가지 방법

### 자동화별 별도 저장소

첫 번째 방법은 namuwiki_trend와 google_finance를 각각 별도 저장소로 관리하는 것입니다. 경계와 배포 독립성은 명확하지만, 공통 Python 환경과 문서 관리가 반복됩니다. 현재 저장소에서 독립 배포가 필요하다는 근거는 확인되지 않았습니다.

### 하나의 Python 패키지에 모든 자동화 포함

두 번째 방법은 하나의 Python 패키지 안에 모든 Collector와 Model을 넣는 것입니다. 초기에는 단순하지만, 서로 다른 데이터 의미와 설정이 섞일 위험이 있습니다.

나무위키 검색어와 주가 데이터는 이름과 의미가 다르므로, 하나의 모델이나 설정으로 묶을수록 경계가 흐려질 수 있습니다.

### Monorepo 안의 독립 패키지

세 번째 방법은 하나의 Git 저장소 안에 여러 Python 패키지를 두는 것입니다. 공통 개발 환경을 공유하면서도 패키지별 데이터 의미를 분리할 수 있습니다. 대신 루트 계층이 새로운 결합 지점이 될 수 있습니다.

이 방식은 현재 automation-hub가 선택한 구조입니다. 이 선택은 과거 모든 대안을 실제로 실험했다는 뜻은 아닙니다. 저장소의 ADR에는 Monorepo를 선택한 결정과 그 결과가 기록되어 있지만, 별도 저장소와 단일 패키지 방식을 장기간 운영했다는 근거는 없습니다. 따라서 이 Chapter에서는 확인된 결정과 가능한 대안을 구분합니다.

## 하나의 저장소와 독립 패키지를 선택한 이유

현재 루트에는 공통 개발 환경과 검증을 위한 요소가 있습니다.

```text
automation-hub/
├── pyproject.toml
├── scripts/verify.py
├── database/
├── docs/
├── namuwiki_trend/
└── google_finance/
```

pyproject.toml과 scripts/verify.py가 대표적인 예입니다. 하나의 .venv와 루트 의존성도 현재 두 패키지가 함께 사용하는 개발 환경입니다.

환경 파일, Docker Compose, Alembic 설정과 공통 문서도 루트에 있습니다. 이 파일들은 모든 도메인의 업무 규칙보다 저장소를 실행하고 검증하는 환경을 설명합니다.

이렇게 공통 환경을 한곳에 두면 새 패키지를 추가할 때 기본 실행과 검증 절차를 다시 만들 필요가 줄어듭니다. 반면 한 패키지의 의존성을 루트 pyproject.toml에 추가하면 전체 개발 환경의 의존성 목록이 커집니다. 현재 구조는 이 비용을 감수하고 환경 단순성을 선택한 상태입니다.

## 루트가 관리하는 것과 패키지가 관리하는 것

현재 파일을 기준으로 루트와 패키지의 책임을 다음처럼 볼 수 있습니다.

```text
Repository Root
├─ Python 버전과 공통 의존성
├─ 공통 검증 설정과 명령
├─ 데이터베이스 공통 기반
├─ 일부 저장 구현
└─ 공통 문서와 설계 결정

Package
├─ 외부 시스템 연결
├─ 패키지 고유 데이터 의미
├─ 수집과 변환 흐름
├─ 실행 흐름
├─ 저장 요구사항
└─ 패키지별 테스트와 CLI
```

패키지는 자신의 데이터 의미와 실행 흐름을 소유하지만, 저장 구현은 패키지 내부와 루트 database/에 나뉘어 있습니다. google_finance는 자신의 수집, 추출·변환, 모델, 저장과 CLI, 테스트를 가지고 있습니다. namuwiki_trend도 자신의 수집, 모델, 실행 흐름, 뉴스·LLM 연결과 테스트를 가지고 있습니다.

두 패키지 사이에 직접적인 실제 실행 코드 import(production import)는 확인되지 않았습니다. google_finance는 자신의 모듈을 주로 import하고, DB 모델에서 루트 database.base.Base를 사용합니다. namuwiki_trend는 자신의 모듈을 중심으로 동작하지만 snapshot 저장과 Daily Trend 조회에서 루트 database 패키지를 사용합니다.

여기서 중요한 예외가 있습니다. 루트 database 패키지는 완전히 중립적인 공통 계층은 아닙니다. database.base, config, engine, session은 공통 데이터베이스 기반에 가깝지만, database.models의 TrendSnapshot과 database.snapshot_save_service는 namuwiki_trend의 데이터 의미를 직접 다룹니다. 특히 snapshot_save_service.py는 namuwiki_trend.models.TrendItem을 import합니다.

따라서 현재 구조를 “두 패키지가 완전히 독립되어 있다”고 설명하면 정확하지 않습니다. 더 정확한 표현은 다음과 같습니다.

> 두 패키지 사이의 직접 기능 의존은 제한되어 있지만, 루트 데이터베이스 패키지에는 공통 기반과 namuwiki_trend에 가까운 코드가 함께 있습니다.

## Flat Layout을 선택한 현재 구조

현재 Python 모듈은 src/ 아래가 아니라 저장소 루트의 namuwiki_trend/, google_finance/, database/ 바로 아래에 있습니다. pyproject.toml에는 설치할 Python 패키지를 찾는 설정(package discovery)이 이 세 패키지를 대상으로 작성되어 있습니다.

이 구조는 현재 규모에서 경로를 이해하기 쉽다는 장점이 있습니다. 코드를 읽을 때 패키지 디렉터리와 import 경로의 관계가 단순하고, 별도의 깊은 packaging 계층을 먼저 이해하지 않아도 됩니다. 기존 Decision Record도 작은 독립 모듈 집합이라는 현재 조건에서 src/ 전환을 보류한 것으로 기록합니다.

다만 Flat Layout이 항상 더 좋은 선택이라는 뜻은 아닙니다. 같은 이름의 파일이나 디렉터리가 있을 때 의도하지 않은 대상이 먼저 import되는 문제(import shadowing)를 주의해야 합니다. 패키지가 커지거나 독립 배포 요구가 생기면 layout을 다시 평가해야 합니다.

## 비슷한 코드를 바로 공통화하지 않은 이유

두 패키지에는 비슷해 보이는 요소가 있습니다. 둘 다 외부 시스템에서 데이터를 읽고, 설정과 로깅을 사용하며, 테스트와 CLI를 가집니다. 그러나 비슷한 모양과 같은 책임은 다릅니다.

공통화를 검토하려면 다음 질문에 답할 수 있어야 합니다.

- 입력과 출력의 의미가 실제로 같은가?
- 두 코드가 같은 이유로 변경되는가?
- 오류 처리와 운영 조건도 같은가?
- 한 패키지의 요구가 다른 패키지의 추상화를 복잡하게 만들지 않는가?

현재 저장소에는 shared/ 패키지가 없습니다. 기존 공통 원칙은 반복 횟수를 기계적인 규칙으로 삼기보다, 실제로 같은 책임이 반복되는지 확인한 뒤 공통화를 검토하는 방식입니다. 반복 횟수는 신호일 뿐이고, 입력·출력·변경 이유와 오류 정책이 함께 같아야 합니다.

작은 중복을 허용하는 이유는 중복이 항상 좋은 선택이어서가 아닙니다. 잘못된 공통 추상화는 패키지의 도메인 결합을 강제하고, 나중에 한쪽의 요구를 다른 쪽이 함께 이해해야 하게 만들 수 있습니다. 현재 두 패키지의 수집 대상과 데이터 의미가 다르므로, 비슷한 이름의 모듈을 먼저 합치지 않았습니다.

이 판단은 영구적인 금지 규칙이 아닙니다. 같은 책임이 실제로 반복되고 공통화의 이점이 결합 비용보다 커질 때 다시 검토할 수 있습니다.

## 현재 구조에서 얻은 것과 감수한 것

현재 Monorepo 구조에서 얻은 것은 다음과 같습니다.

- 한 저장소에서 두 자동화를 함께 탐색하고 검증할 수 있습니다.
- 개발 환경과 기본 품질 기준을 공유할 수 있습니다.
- 패키지별 도메인 경계를 코드 디렉터리로 확인할 수 있습니다.
- 새 자동화를 추가할 때 기존 저장소의 기본 도구를 참고할 수 있습니다.

현재 감수하는 비용도 있습니다.

- 루트 의존성에 패키지별 요구가 함께 들어갑니다.
- 루트 database처럼 공통 기반과 특정 도메인 코드가 섞일 위험이 있습니다.
- 공통화가 늦거나 빠른지 계속 판단해야 합니다.

규모가 커질 때 예상되는 위험도 있습니다.

- 패키지가 늘면 공통 검증 시간이 증가할 수 있습니다.
- 독립 배포가 필요해지면 현재 구조를 다시 검토해야 할 수 있습니다.
- 루트의 도메인 혼합이 커지면 변경 영향 추적이 어려워질 수 있습니다.

## 짧은 회고

다시 시작한다면 두 번째 패키지를 추가하기 전에 루트에 둘 수 있는 코드와 루트에 두어야 하는 코드를 구분해 기록했을 것입니다. `database/`를 검토하면서, 같은 위치에 있다는 사실과 같은 책임을 가진다는 사실은 서로 다르다는 점을 배웠습니다.

## 마무리

automation-hub는 현재 규모에 맞춰 Monorepo 안의 독립 패키지를 선택했습니다. 루트는 개발 환경과 공통 검증을 관리하고, 패키지는 자신의 외부 시스템과 데이터 의미를 관리합니다. 다만 저장 구현은 패키지 내부와 루트 database/에 혼재합니다.

패키지 경계를 정해도 다음 문제가 남습니다. 패키지 내부에서 웹 페이지의 원시 값을 어떻게 검증 가능한 내부 데이터로 바꿀 것인가?
