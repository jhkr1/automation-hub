# Project Handbook Style Guide

## Handbook의 목적

- `automation-hub`를 만들면서 발생한 실제 문제와 설계 의사결정을 설명한다.
- Playwright, SQLAlchemy, Alembic, LLM Provider의 공식 문법을 요약하는 교재가 아니다.
- 기술 자체보다 해당 기술을 선택하게 된 문제와 판단 과정을 설명한다.
- RPA와 Python 중 하나가 절대적으로 우수하다는 결론을 유도하지 않는다.
- 현재 구현된 내용과 향후 계획을 명확히 구분한다.

## 예상 독자

Python 함수와 클래스, 기본 Git, 기본 SQL을 알고 있는 초급 개발자를 기준으로 한다.
Playwright, SQLAlchemy, Alembic, Dependency Injection, Provider, Pipeline,
Application Layer, Domain Model과 Persistence Model의 분리는 처음 접할 수 있다고 가정한다.

## Chapter의 기본 흐름

각 Chapter는 주제에 따라 자연스럽게 구성하되, 다음 사고 흐름을 기본으로 한다.

1. 실제 프로젝트에서 발생한 문제
2. 처음 고려한 방법 또는 기존 접근
3. 선택 가능한 대안
4. 프로젝트가 내린 결정
5. 실제 코드에서의 구현
6. 얻은 점과 감수한 Trade-off
7. 다음 Chapter로 이어지는 질문

모든 항목을 같은 제목으로 반복할 필요는 없다.

## Chapter Scope 규칙

- 각 Chapter는 하나의 중심 질문만 해결한다.
- 이후 Chapter의 주제는 문제만 제시하고 결론까지 설명하지 않는다.
- Chapter를 읽는 데 필수적이지 않은 구현 세부사항은 뒤로 미룬다.
- 한 Chapter가 Handbook 전체의 요약본처럼 되지 않게 한다.

## Progressive Disclosure 규칙

- 실제 문제와 사례를 먼저 보여준 뒤 용어와 구조를 설명한다.
- 초급 독자에게 새로운 전문 용어를 한 문단에서 여러 개 소개하지 않는다.
- 첫 등장에서는 쉬운 표현을 사용하고 공식 용어는 필요한 경우에만 병기한다.
- 상세한 설계는 해당 주제를 다루는 Chapter에서 설명한다.

## 반복 방지 규칙

- 각 핵심 메시지는 한 Chapter에서 한 번의 중심 설명만 둔다.
- 같은 결론을 도입부, 본문, 회고에서 반복하지 않는다.
- 회고 Section은 Chapter 전체 요약이 아니라 당시 판단에서 배운 점만 다룬다.

## 사례 배치 규칙

- 추상적인 구조 설명보다 실제 프로젝트 문제를 먼저 배치한다.
- 사례 뒤에 해당 사례로부터 도출된 설계 판단을 설명한다.
- 코드나 클래스 이름은 독자가 문제를 이해한 뒤 제시한다.

## 문체 규칙

- 저자의 실제 프로젝트 경험에서 출발한다.
- 기본 문체는 독자에게 설명하는 존댓말 평서체(`~합니다`)로 통일한다.
- 회고나 과거의 선택을 설명할 때도 문장 종결을 같은 문체로 유지한다.
- 설명보다 문제를 먼저 보여준다.
- “X란 무엇인가”로 Chapter를 시작하지 않는다.
- 백과사전식 도입과 과장된 주장을 피한다.
- 설계 결과뿐 아니라 그 결과에 도달한 과정을 보여준다.
- 검증되지 않은 내용과 구현되지 않은 기능을 현재 사실처럼 쓰지 않는다.
- RPA, Python 또는 특정 기술을 일방적으로 평가하지 않는다.
- 같은 표현과 문장 구조를 반복하지 않는다.

## Markdown 규칙

- Chapter 제목은 `# Chapter N. 제목` 형식을 사용한다.
- 주요 절은 `##`, 하위 절은 필요한 경우에만 `###`를 사용한다.
- 코드 블록에는 언어를 지정한다.
- 단순한 흐름은 `text` 코드 블록을 사용한다.
- Mermaid와 표는 설명을 실질적으로 돕는 경우에만 사용한다.
- Callout 문법과 Front Matter는 현재 사용하지 않는다.
- 장식적인 이모지와 과도한 구분선을 사용하지 않는다.

## 코드 예제 규칙

- 실제 저장소의 코드와 일치하는 예제를 우선한다.
- 설명을 위해 단순화한 예제는 그렇게 밝혀야 한다.
- 존재하지 않는 클래스, 메서드, 경로를 실제 구현처럼 쓰지 않는다.
- 긴 코드를 복사하지 말고 설계 판단을 보여주는 최소 범위만 인용한다.
- 코드보다 문제와 설계 의도를 먼저 설명한다.

## Chapter 마무리 규칙

- 핵심 메시지를 짧은 문단으로 정리한다.
- 번호형 Summary를 기계적으로 반복하지 않는다.
- 다음 Chapter가 해결할 질문을 자연스럽게 제시한다.
- 다음 Chapter의 내용을 과도하게 미리 설명하지 않는다.
