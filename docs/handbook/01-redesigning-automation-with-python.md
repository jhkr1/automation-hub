# Chapter 1. 업무 자동화를 Python 시스템으로 다시 설계하기

Automation Anywhere로 업무 자동화를 개발하면서, 같은 작업을 Python으로 다시 구현하면 무엇이 달라지는지 직접 확인해 보고 싶었습니다. 목표는 RPA가 부족하다는 결론을 내리는 것이 아니었습니다. 화면을 중심으로 구성된 자동화가 Python의 명시적인 데이터 모델, 테스트, 오류 처리와 만나면 어떤 구조로 바뀌는지를 비교해 보고 싶었습니다. 한 번 실행되는 작업을 만드는 것과 여러 번 실행해도 결과를 확인하고 수정할 수 있는 시스템을 만드는 것은 서로 다른 문제라는 생각에서 `automation-hub`를 시작했습니다.

처음에는 기존 업무 흐름을 Python 코드로 옮기면 된다고 생각했습니다. 페이지를 열고, 필요한 값을 읽고, 파일에 저장하면 자동화가 완성될 것처럼 보였습니다. 하지만 실제로 구현을 시작하자 “무엇을 읽어야 하는가”부터 다시 정의해야 했습니다. 나무위키의 초기 HTML에는 실시간 검색어가 없었고, 브라우저가 JavaScript를 실행한 뒤에야 필요한 목록이 나타났습니다. Google Finance에서도 페이지 전체 텍스트만으로는 가격과 통화를 정확히 구분하기 어려웠습니다.

예상하지 못했던 문제는 화면 수집에서 끝나지 않았습니다. 수집한 값이 올바른지 검증해야 했고, 가격을 어떤 숫자 형식으로 다룰지 결정해야 했습니다. 수집 시각의 기준, 여러 번 실행한 결과의 저장 방식, 외부 서비스 오류의 처리 방식도 정해야 했습니다.

자동화는 단순한 화면 조작이 아니라 외부 시스템의 불확실한 데이터를 내부의 신뢰할 수 있는 데이터로 바꾸는 작업이었습니다. 이 Chapter에서는 그 관점이 생긴 과정과 Python으로 다시 설계하면서 얻은 점과 감수한 점을 설명합니다.

## 자동화가 동작하는 것과 유지되는 것은 다릅니다

화면 자동화가 한 번 성공하는 것과 반복 실행 가능한 시스템이 되는 것은 다릅니다. 다음과 같은 작업이 하나의 긴 흐름으로 묶여 있다고 가정해 보겠습니다.

```text
웹 페이지 열기
→ 목록 읽기
→ 각 항목에 대해 뉴스 검색
→ AI에게 설명 요청
→ 결과를 파일에 저장
```

이 흐름이 실패했을 때 원인은 여러 가지일 수 있습니다.

- 페이지가 열리지 않았을 수 있습니다.
- 목록의 개수나 형식이 기대와 다를 수 있습니다.
- 뉴스 응답이 잘못되었을 수 있습니다.
- AI 호출이나 파일 저장에서 문제가 발생했을 수 있습니다.

화면 중심 자동화에서는 이 문제가 하나의 작업 실패로 보이기 쉽습니다. 구현을 시작하면서, 작업을 화면 순서가 아니라 외부 값을 확인하고 내부 결과로 바꾸는 흐름으로 다시 바라보게 되었습니다.

```text
수집
    ↓
검증과 변환
    ↓
내부 데이터
    ↓
저장 또는 추가 처리
```

이 구분은 파일을 여러 개로 나누기 위한 규칙이 아닙니다. 어느 지점에서 문제가 발생했는지 설명하고, 외부 시스템의 변화와 내부 판단을 구분하기 위한 관점입니다. 뒤의 Chapter에서는 이 질문을 각 Package의 실제 구조로 확인합니다.

## 화면 순서만으로는 답할 수 없었던 질문

기존 자동화의 화면 순서를 그대로 보존하는 대신, 업무가 실제로 어떤 입력을 받고 어떤 결과를 만들어 내는지 다시 확인했습니다.

“나무위키의 실시간 검색어 10개를 가져온다”는 요구는 화면에서 다음처럼 보일 수 있습니다.

```text
페이지 접속
→ 검색어 영역 확인
→ 목록 복사
→ 파일 저장
```

하지만 시스템으로 만들려면 다음 질문에 답해야 합니다.

- 검색어는 초기 HTML에 있는가, 브라우저 실행 이후에 나타나는가?
- 어떤 영역이 실제 검색어 목록인가?
- 목록의 시작과 끝을 어떻게 확인할 것인가?
- 항목이 기대한 개수인지 어떻게 알 것인가?
- 각 링크의 형식이 올바른지 확인할 것인가?

실제 조사에서 나무위키의 초기 HTML에는 실시간 검색어가 없었습니다. 브라우저가 JavaScript를 실행한 뒤의 DOM을 확인해야 했습니다. 따라서 단순히 HTML 문자열을 읽는 문제가 아니라, 렌더링된 화면에서 어떤 영역을 신뢰할지 결정하는 문제가 되었습니다.

`namuwiki_trend`에서는 목록을 읽는 것만으로 결과가 올바르다고 가정하지 않습니다. 순위가 보존되는지, 목록의 시작과 끝이 기대한 구조인지, 항목 개수와 링크 형식이 맞는지를 확인해야 합니다. 목록의 끝을 확인하기 위한 표시 값도 데이터와 구분해야 합니다. 구체적인 검증 방식은 이후 수집과 데이터 변환을 다루는 Chapter에서 설명합니다.

Google Finance에서도 비슷한 문제가 나타났습니다. 페이지 전체 텍스트에는 가격과 통화 외에 다른 정보가 함께 포함될 수 있었습니다. 전체 텍스트를 한 번에 읽는 방식으로는 현재 가격과 이전 가격, 통화를 안전하게 구분하기 어려웠습니다.

그래서 다음 질문을 다시 정의해야 했습니다.

- 가격 문자열을 어떤 숫자 형식으로 다룰 것인가?
- 통화는 페이지의 어느 영역에서 읽을 것인가?
- 화면에서 읽은 값과 시스템 내부에서 사용할 값은 같은가?
- 수집 시각은 어떤 시간 기준으로 보존할 것인가?

화면에서 읽은 값은 그대로 최종 데이터가 되지 않았습니다. 외부 문자열은 검증과 변환을 거쳐 내부에서 의미를 가진 데이터가 되어야 했습니다.

이 차이를 구분하지 않으면 화면이 조금만 바뀌어도 저장된 결과의 의미가 흔들립니다. 반대로 화면에서 얻은 원시 값과 내부에서 사용할 값을 구분하면, 외부 시스템의 변화와 업무 규칙의 변화를 서로 다른 문제로 다룰 수 있습니다. 이 구분이 Python으로 다시 설계하는 출발점이 되었습니다.

## Python으로 다시 설계한 이유

Python을 선택한 이유는 Python이 RPA보다 우수하기 때문이 아닙니다. 해결하려는 문제가 달랐기 때문입니다. 화면을 중심으로 구성된 작업을 유지하려면, 화면 조작 자체보다 그 결과를 어떤 규칙으로 해석하고 검증할지 명시해야 했습니다.

`automation-hub`에서는 다음 질문에 코드로 답할 수 있어야 했습니다.

- 외부에서 읽은 값을 어떤 내부 데이터로 표현하는가
- 잘못된 값은 어느 단계에서 거부하는가
- 외부 시스템의 실패와 내부 규칙의 실패를 어떻게 구분하는가
- 반복 실행 결과를 어떻게 확인할 수 있는가

이 과정에서 화면을 다루는 부분과 업무 규칙을 다루는 부분을 분리해서 생각하게 되었습니다. 브라우저가 필요한 작업은 브라우저 경계에서 수행하고, 문자열 검증과 데이터 변환은 외부 사이트 없이도 확인할 수 있는 규칙으로 만들었습니다.

내부 데이터에는 화면에 표시된 문자열보다 구체적인 의미가 필요합니다. 예를 들어 가격은 단순한 텍스트가 아니라 숫자로 다뤄야 하고, 수집 시각은 어느 시간 기준인지 알 수 있어야 합니다. `google_finance`에서 가격을 `Decimal`로 다루고 수집 시각을 timezone-aware datetime으로 표현한 것은 이러한 데이터 의미를 코드에 남기기 위한 선택입니다.

화면에서 읽은 업무 데이터와 데이터베이스에 저장할 데이터가 항상 같은 형태일 필요도 없었습니다. 중요한 것은 두 표현이 어떤 관계를 가지는지 명확히 하는 것입니다. 저장 구조의 구체적인 선택은 이후 Persistence Chapter에서 다룹니다.

외부 오류도 하나의 실패로 뭉뚱그릴 수 없었습니다. 일시적으로 다시 시도할 수 있는 오류와 입력 자체가 잘못된 오류를 구분해야 했습니다. 무조건 재시도하면 원래의 문제를 숨길 수 있기 때문입니다. 이 Chapter에서는 이러한 문제의식만 남기고, 구체적인 오류 처리 정책은 이후 외부 서비스 Chapter로 넘깁니다.

## 이 프로젝트가 해결하려는 문제

현재 `namuwiki_trend`와 `google_finance`는 서로 다른 외부 시스템을 다룹니다.

```text
namuwiki_trend
    └─ 동적으로 렌더링되는 검색어와 뉴스 문맥

google_finance
    └─ 브라우저에서 수집한 종목 시세
```

두 자동화에서 공통으로 확인한 문제는 외부 데이터를 가져오는 것만으로 작업이 끝나지 않는다는 점입니다. 가져온 값이 올바른지 확인하고, 내부에서 사용할 형태로 바꾸고, 실행 결과를 다시 확인할 수 있어야 합니다.

이 관점에서 `automation-hub`는 화면 작업을 코드로 복사하는 프로젝트가 아닙니다. 외부 시스템의 불확실한 데이터를 내부의 설명 가능한 데이터로 바꾸고, 실패한 위치를 추적할 수 있는 자동화를 만드는 프로젝트입니다.

서로 다른 자동화를 하나의 저장소에서 관리하기 시작하자, 무엇을 함께 관리하고 무엇을 분리해야 하는지가 다음 설계 문제가 되었습니다. 이 질문은 Chapter 1에서 결론 내리지 않고 다음 Chapter로 넘깁니다.

## 얻은 것과 감수한 것

Python 시스템으로 다시 설계하면서 다음을 얻었습니다.

- 데이터의 의미를 코드로 확인할 수 있게 되었습니다.
- 실패가 발생한 위치를 구분하기 쉬워졌습니다.
- 외부 시스템과 내부 규칙을 분리해서 검증할 수 있게 되었습니다.
- 반복 실행 결과를 설명하고 비교하기 쉬워졌습니다.

대신 다음을 감수해야 했습니다.

- 초기 설계에 더 많은 시간이 필요해졌습니다.
- 테스트와 문서 작성이 개발 과정에 포함되었습니다.
- 브라우저와 데이터베이스 같은 운영 의존성을 관리해야 했습니다.
- Python을 사용해도 잘못된 추상화는 구조를 더 복잡하게 만들 수 있었습니다.

이 선택은 자동화를 더 짧게 만드는 방법이 아니었습니다. 자동화가 무엇을 알고 무엇을 보장하는지 설명할 수 있게 만드는 방법이었습니다.

## 짧은 회고

다시 시작한다면 기술을 먼저 정하기보다, 외부 시스템에서 무엇을 확인했고 어떤 데이터 계약이 필요한지부터 더 일찍 기록했을 것입니다. 화면이 보인다는 사실과 시스템이 올바른 데이터를 얻었다는 사실은 같지 않았기 때문입니다.

처음부터 완벽한 구조를 만드는 것보다, 현재 알고 있는 사실과 아직 확인하지 못한 가정을 구분하는 일이 더 중요하다는 점도 배웠습니다. Python은 자동으로 유지보수성을 보장하지 않습니다. 유지보수성은 선택한 기술보다 문제와 책임을 명확히 설명할 수 있는지에 달려 있습니다.

## 마무리

`automation-hub`는 기존 화면 중심 자동화를 Python으로 다시 구현하면서, 자동화를 데이터와 실패 경계를 가진 시스템으로 바라보게 된 프로젝트입니다. Playwright나 데이터베이스 같은 기술은 목적이 아니라 이 문제를 해결하기 위한 선택이었습니다.
