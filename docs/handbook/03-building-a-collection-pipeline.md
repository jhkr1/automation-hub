# Chapter 3. 외부 데이터를 검증 가능한 내부 데이터로 바꾸기

`namuwiki_trend`를 구현하면서 초기 HTML에 실시간 검색어가 없다는 사실을 확인했고, `google_finance`에서는 페이지 전체 텍스트만으로 가격과 통화를 구분하기 어려웠습니다. 브라우저에서 값이 보인다는 사실과, 그 값을 시스템이 믿고 사용할 수 있다는 사실은 달랐습니다. 화면에는 여러 문자열이 섞여 있고, 일부 값이 누락되어도 브라우저 자체는 오류를 내지 않을 수 있습니다.

나무위키와 Google Finance를 수집하면서 같은 질문을 반복해서 만났습니다.

- 지금 읽은 값이 정말 필요한 항목인가?
- 문자열의 공백, 기호와 형식을 어떻게 판단할 것인가?
- 목록의 개수나 가격의 단위를 어떻게 확인할 것인가?
- 문제가 브라우저에 있는지, 데이터에 있는지, 내부 규칙에 있는지 어떻게 구분할 것인가?

이 질문에 답하려면 외부 화면의 값을 바로 업무 로직에 넘길 수 없었습니다. 외부 시스템에서 읽는 단계, 읽은 값을 확인하고 바꾸는 단계, 내부에서 사용할 데이터의 형태를 정하는 단계를 구분해야 했습니다.

## 화면에서 읽은 값은 아직 데이터가 아닙니다

나무위키의 실시간 검색어는 JavaScript가 실행된 뒤의 DOM에 나타났습니다. 따라서 Collector는 브라우저에서 페이지를 열고, 예상한 목록과 항목이 실제로 존재하며 보이는지 확인하는 책임을 맡았습니다. 화면 구조가 바뀌거나 필요한 값이 누락되면 수집 단계에서 알아차릴 수 있어야 했습니다.

현재 `namuwiki_trend/collector.py`는 Playwright로 페이지 응답과 필요한 DOM 요소의 개수를 확인한 뒤 원시 keyword와 링크를 읽습니다. 페이지 응답이 없거나 상태 코드가 200이 아니거나, 필요한 요소가 기대와 다르면 수집 단계에서 실패합니다.

그 뒤의 문제는 목록이 읽혔다는 사실만으로 해결되지 않습니다. `namuwiki_trend/extraction.py`는 원시 항목의 타입, 공백, 링크 형식과 목록 개수를 확인하고 검증된 `TrendItem`으로 바꿉니다. 현재 페이지에 목록의 끝을 확인하기 위한 표시 값이 있다는 사실도 이 단계에서 처리합니다.

이 규칙은 화면의 목록을 그대로 저장하지 않고, “검증된 Top 10 순위 목록”이라는 내부 의미를 만드는 과정입니다. 목록 개수나 끝을 확인하는 조건이 맞지 않으면 일부 결과를 조용히 사용하는 대신 실패합니다. 잘못된 결과를 정상 결과처럼 전달하는 비용이 더 크기 때문입니다.

Google Finance에서는 가격, 이전 종가, 시가와 통화 정보가 한 화면의 여러 문자열로 섞여 있었습니다. `$338.19`라는 문자열만으로는 해당 값의 통화와 항목 이름을 확정할 수 없습니다.

`google_finance/collector.py`는 먼저 입력 symbol을 `strip()`하고 대문자로 정규화한 뒤, 거래소와 종목 형식인지 확인합니다. 이후 symbol에 해당하는 영역으로 locator 범위를 좁히고, 현재 가격·변동률·종목명·통화 metadata·이전 종가·시가를 각각 원시 문자열로 읽습니다. 이 단계의 결과는 아직 숫자 계산에 사용할 `StockPrice`가 아니라 `RawStockQuote`입니다.

이때 문자열을 그대로 다음 단계에 넘기지 않고, 형식과 의미를 확인한 뒤 내부 계약으로 변환해야 했습니다. `google_finance/extraction.py`는 가격·변동률·통화 문자열을 각각 검증하고, 변환이 끝난 결과를 `StockPrice`로 만듭니다. 그 결과 가격과 변동률, 통화와 수집 시각을 화면 표현과 분리해 다룰 수 있습니다.

두 사례는 모두 외부 값의 의미를 내부에서 다시 확인해야 한다는 점에서는 같습니다. 그러나 검증 규칙은 서로 다릅니다. 나무위키는 순위 목록의 개수와 링크 형식이 중요하고, Google Finance는 가격 표현과 통화 metadata, 시간 정보가 중요합니다. 따라서 두 수집기를 하나의 범용 파서로 합치는 대신, 각 패키지가 자신의 데이터 의미를 검증하도록 두었습니다.

## 수집과 변환의 책임을 나누기

이 프로젝트에서 외부 값을 내부 데이터로 바꾸는 흐름은 다음과 같습니다.

```text
외부 페이지
    ↓
수집: 브라우저와 DOM에서 원시값 읽기
    ↓
검증·변환: 형식, 개수, 의미 확인
    ↓
내부 데이터 모델
    ↓
다음 실행 흐름 또는 저장
```

여기서 수집 단계(Collector)는 외부 시스템과 직접 대화하며 원시값을 읽습니다. 검증·변환 단계(Extraction)는 페이지를 조작하지 않고 그 값이 내부 규칙에 맞는지 확인합니다. 따라서 “무엇을 읽었는가”와 “무엇을 내부 데이터로 인정할 것인가”를 나누어 판단할 수 있습니다.

다만 실제 구현은 두 패키지에서 완전히 같은 순서로 배치되어 있지 않습니다. `namuwiki_trend/collector.py`는 원시 항목을 읽은 뒤 `validate_and_rank_items`를 호출하고 최종적으로 `TrendItem` 목록을 반환합니다. `google_finance/collector.py`는 `RawStockQuote`를 반환하고, `google_finance/pipeline.py`의 `StockPricePipeline`이 `parse_stock_quote`를 호출해 `StockPrice`로 변환합니다.

이 차이를 숨기고 “모든 패키지는 반드시 같은 계층을 가져야 한다”고 말할 필요는 없습니다. 중요한 것은 모듈 이름의 통일이 아니라 외부 값의 수집과 내부 계약의 검증을 구분하는 것입니다. 실제 코드에서는 이 구분이 함수와 모듈의 책임으로 나타나며, 패키지의 데이터 특성에 따라 호출 위치가 달라집니다.

## 내부 데이터 모델이 필요한 이유

문자열을 다음 단계로 계속 전달하면 각 함수가 같은 문자열을 서로 다르게 해석할 수 있습니다. 그래서 수집 직후에 내부 데이터 모델을 만들고, 이후 단계는 화면의 문법보다 모델의 의미를 다루도록 했습니다.

나무위키의 `TrendItem`은 순위, keyword와 링크를 하나의 불변 데이터로 표현합니다. `validate_and_rank_items`가 순위를 부여한 뒤 반환하므로, 이후 코드는 화면의 항목 위치를 다시 추측하지 않아도 됩니다. Google Finance에는 원시 문자열을 담는 `RawStockQuote`와 검증·변환된 `StockPrice`가 따로 있습니다. `StockPrice`는 `Decimal` 가격과 명시적인 통화, timezone-aware 수집 시각을 요구합니다.

이 모델들은 외부 입력이 내부에서 어떤 형태로 인정되는지를 명확히 하는 계약입니다. 예를 들어 Google Finance의 수집 시각에 시간대 정보가 없으면 `StockPrice`가 거부하고, 가격 문자열이 숫자 형식이 아니면 변환 단계가 실패합니다. 오류를 다음 단계까지 넘기기 전에 확인할 수 있는 이유입니다.

## Pipeline은 흐름을 조정합니다

수집과 변환을 분리하면 두 단계를 어떤 순서로 연결할지도 정해야 합니다. 이 역할을 하는 것이 실행 순서를 조정하는 계층(Pipeline 또는 orchestration)입니다. Pipeline은 외부 DOM을 직접 읽거나 문자열 규칙을 다시 구현하지 않습니다.

Google Finance의 `StockPricePipeline`은 symbol을 Collector에 전달하고, 반환된 `RawStockQuote`를 `parse_stock_quote`에 넘깁니다. `namuwiki_trend`의 `TrendPipeline`은 Collector가 반환한 `TrendItem` 목록을 순서대로 다음 처리 단계에 전달합니다. 현재 전체 실행은 각 패키지의 `main.py`에서 시작합니다. Google Finance CLI는 Pipeline을 실행한 뒤 검증된 `StockPrice`를 출력하고, namuwiki_trend의 main은 Collector와 이후 처리 객체를 조립해 실행합니다.

Pipeline이 필요한 이유는 Collector가 브라우저와 내부 업무 규칙을 모두 알아야 하는 상황을 피하기 위해서입니다. Collector는 외부 값을 가져오고, 변환 단계는 그 값을 확인하며, Pipeline은 두 작업의 순서만 조정합니다. 계층을 늘리는 것이 목적이 아니라 각 단계의 변경 이유를 분리하는 것이 목적입니다.

## 분리하면 검증할 수 있는 범위가 늘어납니다

수집과 변환을 한 함수에 모두 넣으면 브라우저가 있어야만 문자열 규칙을 확인할 수 있습니다. 반대로 현재 구조에서는 `tests/namuwiki_trend/test_extraction.py`와 `tests/google_finance/test_extraction.py`가 브라우저 없이 변환 규칙을 확인하고, Pipeline 테스트는 Collector가 반환한 값이 다음 단계로 전달되는지를 확인합니다. Collector 테스트는 브라우저 경계의 응답과 DOM 상황을 별도로 다룹니다.

이렇게 나누면 각 경계의 입력과 결과를 외부 환경 없이 확인할 수 있습니다. 상세한 테스트 수준과 실제 환경 검증은 Chapter 8에서 다룹니다.

## 실패 위치를 구분하기

외부 자동화에서는 “실패했다”는 결과만으로는 원인을 찾기 어렵습니다. 이 프로젝트에서는 실패가 발생한 경계를 구분해 다음 단계로 넘깁니다.

- 브라우저 경계: 페이지 응답, 상태 코드, timeout, DOM 요소의 개수와 가시성을 확인합니다.
- 데이터 경계: 문자열 타입, 공백, 링크 형식, 숫자와 통화 형식을 확인합니다.
- 내부 규칙 경계: Top 10 개수, 순위, timezone-aware 시각과 같은 모델 조건을 확인합니다.
- 실행 경계: Pipeline은 Collector나 변환 단계의 예외를 임의로 정상 데이터로 바꾸지 않고 전달합니다. CLI는 프로세스 경계에서 오류를 메시지와 종료 코드로 드러냅니다.

이 구분은 모든 오류를 미리 복구하려는 설계가 아닙니다. 먼저 어느 경계에서 신뢰할 수 없는 값이 되었는지를 알 수 있게 하는 설계입니다. 브라우저가 페이지를 받지 못한 문제와 페이지는 받았지만 통화 정보가 모호한 문제는 원인과 대응이 다르기 때문입니다.

## 얻은 것과 감수한 것

이 구조를 통해 외부 시스템과 내부 규칙을 분리할 수 있었습니다. 추출 함수는 브라우저 없이 입력값의 규칙을 확인할 수 있고, Collector는 브라우저 경계의 문제를 따로 다룰 수 있습니다. 내부 모델은 데이터의 의미를 코드로 남기며, 실패 위치를 따라가기도 쉬워졌습니다. 각 단계의 입력과 출력이 분명해지면서 어떤 값이 화면에서 왔고 어떤 값이 검증을 통과했는지도 설명할 수 있습니다.

대신 구조는 단순한 화면 스크립트보다 복잡해졌습니다. 원시 데이터를 담는 형태와 내부 데이터를 담는 형태를 나누어야 하고, 수집·검증·조정이라는 여러 책임을 관리해야 합니다. 초기에는 화면을 읽고 바로 출력하는 방식보다 설계와 확인에 시간이 더 필요합니다. 그러나 외부 시스템의 작은 변화가 내부 데이터의 의미를 조용히 바꾸는 위험을 줄이려면 이 비용을 감수할 이유가 있습니다.

## 짧은 회고

다시 시작한다면 화면에서 읽은 값의 목록을 먼저 만들기보다, 각 값이 내부에서 어떤 의미를 가져야 하는지부터 기록했을 것입니다. 수집 규칙은 화면에 종속되지만, 검증해야 할 데이터 계약은 이후 단계의 기준이 되기 때문입니다.

## 마무리

이 프로젝트에서 수집은 브라우저에서 값을 읽는 일로 끝나지 않습니다. 외부 값을 읽고, 그 값이 기대한 형식과 의미를 가지는지 확인하고, 내부 모델로 바꾼 뒤 다음 흐름에 전달해야 합니다. `namuwiki_trend`와 `google_finance`는 검증 규칙과 호출 배치가 다르지만, 외부 데이터와 내부 데이터 사이에 명시적인 경계를 둔다는 점을 공유합니다.

내부 데이터를 만들었다면, 이제 이 데이터를 어디에, 어떤 형태로 저장해야 하는가?
